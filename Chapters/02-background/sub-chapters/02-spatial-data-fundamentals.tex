\section{Geometry and indexing}
\subsection{Geometry model and encodings}
\label{sec:geometry-model-encodings}
The geospatial workloads benchmarked in this thesis share a geometric model rooted in the \acrfull{ogc} Simple Feature Access specification \parencite{herring2011_simple_feature_access_part1}, adopted internationally as \parencite{iso2004_19125_1_simple_feature_access}. \textcite{herring2011_simple_feature_access_part1} defines a base Geometry type with seven concrete subtypes that recur throughout the thesis: \texttt{Point}, \texttt{LineString}, and \texttt{Polygon} for individual zero-, one-, and two-dimensional features; \texttt{MultiPoint}, \texttt{MultiLineString}, and \texttt{MultiPolygon} for homogeneous collections of those primitives; and \texttt{GeometryCollection} for heterogeneous aggregates. Each instance has a coordinate dimension that may extend beyond the planar $(X, Y)$ pair with an optional Z ordinate, used for elevation when interpreted under a vertical or compound \acrfull{crs}, the latter pairing a horizontal \acrshort{crs} with an independent vertical one \parencite{iso2019_19111_referencing_by_coordinates}, and an optional M ordinate carrying a per-vertex measure value, commonly a distance measured along a linear feature, yielding the XYZ, XYM, and XYZM variants used by formats covered later \parencite{herring2011_simple_feature_access_part1}.

Two interchange encodings govern how these values move between formats and engines. \acrfull{wkt} is a human-readable serialization in which a geometry is written as a type tag followed by parenthesized coordinate tuples \parencite{herring2011_simple_feature_access_part1}. Its compact binary counterpart, \acrfull{wkb}, encodes the same logical content as a typed sequence of fixed-width fields, a layout in which each component occupies a known number of bytes so a reader can locate it without scanning what precedes it, with byte order declared as little- or big-endian to fix how multi-byte numeric values are arranged, suiting the encoding to both on-disk storage and on-the-wire transfer, the form data takes while moving across a network \parencite{herring2011_simple_feature_access_part1}. PostGIS defines the Extended variants \acrfull{ewkt} and \acrfull{ewkb}, which prepend an \texttt{SRID=n;} block (a \acrfull{srid} prefix) to the textual form and embed the same identifier together with explicit Z and M flags in the binary form \parencite{postgis2024_manual_34, geos2021_wkb_specification}. Several of the binary on-disk encodings covered later in this thesis embed \acrshort{wkb} or a close derivative as the geometry payload, the geometry bytes themselves, wrapping it in format-specific framing, the headers and length prefixes the outer format requires \parencite{postgis2024_manual_34, ogc2024_geopackage_encoding_standard_140, ogc2024_geoparquet_specification_v110}.

Each geometry value is interpreted with respect to a \acrshort{crs}, defined as a coordinate system related to an object by a datum \parencite{herring2011_simple_feature_access_part1, lott2021_ogc_topic2_referencing_by_coordinates}. The term \acrfull{srs} appears in the \acrshort{ogc} Simple Features and PostGIS lineage with the same intended meaning and is treated as a near-synonym throughout this thesis \parencite{herring2011_simple_feature_access_part1, postgis2024_manual_34}. The \acrshort{srid} is the integer that tags each geometry with the \acrshort{crs} in which its coordinates should be read, typically by reference to a code in the \acrshort{epsg} Geodetic Parameter Dataset \parencite{herring2011_simple_feature_access_part1, postgis2024_manual_34, iogp2024_epsg_dataset}.

\subsection{Spatial indexing}
\label{sec:spatial-indexing}
The encodings introduced above make geometries storable and exchangeable but leave open how a query engine finds the geometries that match a predicate. That role falls to indexes, which let an engine skip data without reading it. A spatial index plays this role for a geometry column, but the data it organizes is two-dimensional and cannot be arranged in a single linear sequence the way one-dimensional values can \parencite{guttman1984_rtree_dynamic_index}. To make pruning tractable, every spatial structure considered below approximates each geometry by its minimum bounding rectangle, also called the bounding box or envelope, defined as the smallest axis-aligned rectangle that contains the geometry \parencite{herring2011_simple_feature_access_part1}. Spatial query evaluation then follows a filter--refine pattern in which the index returns candidates whose bounding boxes intersect the query region, and the engine applies the exact geometric predicate only to that reduced set \parencite{orenstein1986_spatial_query_processing}. The structures introduced below differ only in how they organize these rectangles.

The dominant family of spatial indexes is tree-based \parencite{gaede1998_multidimensional_access_methods}. The R-tree, introduced by \textcite{guttman1984_rtree_dynamic_index}, is the foundational structure: each indexed geometry sits in a leaf together with its bounding box, and internal nodes store rectangles enclosing all bounding boxes in their children, producing a height-balanced hierarchy in which a query rectangle is compared against only a small subset of nodes from the root downward, as Figure \ref{fig:r-tree-indexing} illustrates. Many later refinements adjust how rectangles are grouped to keep the directory tight \parencite{gaede1998_multidimensional_access_methods}, the most prominent being the R*-tree of \textcite{beckmann1990_rstar_tree_efficient_robust}. Such tree-based indexes are often delivered through an extensible framework that abstracts the operations shared by tree indexes, the canonical example being the \acrfull{gist} of \textcite{hellerstein1995_generalized_search_trees_database_systems}, which hosts R-trees, B$^{+}$-trees for one-dimensional ordered data, and other tree-based access methods through one implementation.

Whereas R-trees partition the data, where each rectangle ends up in exactly one leaf, a parallel family partitions the space itself, assigning regions of the plane to nodes independently of which geometries fall in them \parencite{gaede1998_multidimensional_access_methods}. The quadtree of \textcite{finkel1974_quad_trees_composite_keys} is the canonical case: it recursively subdivides the plane into four equal quadrants, splitting each quadrant again whenever its contents exceed a fixed capacity, with many variants developed for points, regions, and rasters \parencite{samet1984_quadtree_hierarchical_data_structures}. The KDB-tree of \textcite{robinson1981_kdb_tree_search_structure} descends from the k-d tree of \textcite{bentley1975_multidimensional_binary_search_trees}, a binary tree that recursively splits multidimensional space one axis at a time, and adapts it to fixed-size disk pages by grouping alternating axis-aligned splits into B-tree-like pages. The simplest member of the family is the uniform grid \parencite{gaede1998_multidimensional_access_methods}, which divides the plane into equal-sized cells. It offers no balance guarantees, but the cell of any geometry can be computed from its coordinates without tree traversal, so different workers can handle their share independently without coordination \parencite{yu2019_geospark_perspective_beyond}.

A complementary mechanism in the column-oriented file formats used by cloud-native analytics, which store data column-by-column rather than row-by-row, prunes at the level of a contiguous block of rows rather than at the level of an individual geometry. Each block carries a small summary of its contents, known as a zonemap in the database literature \parencite{moerkotte1998_small_materialized_aggregates}, and a query engine consults this summary before reading the block, skipping it whenever the predicate cannot be satisfied \parencite{lamb2022_querying_parquet_millisecond_latency}. The spatial extension stores a bounding box for each block alongside the scalar statistics, so that a spatial predicate is evaluated against the block envelope before any geometries are read \parencite{ogc2024_geoparquet_specification_v110}. This serves the same role as a tree-based index, but at a coarser granularity.
