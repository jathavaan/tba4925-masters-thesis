\section{Cloud-native data architecture}

\subsection{Storage and compute decoupling}
Traditional data processing systems were designed under the assumption that storage and computation live on the same machine (i.e., a node). Data storage and computation are tightly coupled, meaning it processes only the data stored on that node. Both storage and compute must scale together, even when demand grows at different rates due to this tight coupling \parencite{dageville2016_snowflake_elastic_data_warehouse}. 

Cloud architecture decouples the computation and storage into separate layers, as illustrated in Figure~\ref{fig:storage-compute-architectures}. The data is stored in object storage, and provisioning compute resources is independent and on-demand. Object storage is inexpensive and more or less limitless in capacity, but it lacks query capabilities. The decoupling allows storage and compute to be scaled, priced, and allocated independently \parencite{pang2024_storage_disaggregated_databases}. The computation can be shut down entirely when not in use \parencite{dageville2016_snowflake_elastic_data_warehouse}. The separation of the compute and storage of data layers allow multiple compute engines to read the same underlying data without coordination through a shared server \parencite{pang2024_storage_disaggregated_databases}. \textcite{dageville2016_snowflake_elastic_data_warehouse} points out that this decoupled architecture incurs higher latency and CPU overhead per request than a node where compute and storage are tightly coupled. This makes format design critical, where formats that minimize data reads per query gain an advantage in this architecture.

\subsection{Object storage and HTTP access}
Object storage is the shared layer underlying these architectures. It organizes data as opaque objects identified by a key within a flat container namespace, accessed via a network API rather than POSIX file system calls \parencite{mesnier2003_object_based_storage, calder2011_windows_azure_storage}. Commercial implementations such as Azure Blob Storage expose each object as an \acrshort{https} \acrshort{url} and are accessed over \acrshort{http} \parencite{microsoft2024_azure_blob_introduction}.

Reading is mediated by \acrshort{http} itself. \textcite{fielding2022_rfc9110_http_semantics} standardizes the \texttt{Range} request header, which lets a client retrieve an arbitrary byte interval of a remote resource without downloading the whole file. Operational experience confirms the viability of this access model for analytical workloads at scale \parencite{vuppalapati2020_snowflake_elastic_query_engine,durner2023_exploiting_cloud_object_storage}. Cloud-native data formats are designed around this access pattern: layout metadata is placed at a known offset within the object so that readers can fetch it first, after which range requests retrieve only the byte intervals needed by the query \parencite{maso2023_ogc_cog_standard}, as illustrated in Figure~\ref{fig:http-range-requests}.

\subsection{Distributed- and non-distributed compute}
\label{sec:distributed-and-non-distributed-compute}
With storage and compute decoupled, the choice of compute model becomes a central architectural decision. Non-distributed compute executes a query entirely within a single process on one machine, with no coordination overhead between workers \parencite{mcsherry2015_scalability_but_at_what_cost}. Distributed compute, by contrast, splits both data and computation across multiple worker nodes coordinated by a driver or scheduler \parencite{stonebraker1986_case_for_shared_nothing}. This distribution introduces overhead. Task scheduling, data shuffling between nodes, serialization, and network communication between workers, all of which add latency before any computation begins \parencite{mcsherry2015_scalability_but_at_what_cost}. As a result, distributed systems only outperform single-node systems when the dataset or computation is large enough to justify the coordination cost \parencite{mcsherry2015_scalability_but_at_what_cost}. For spatial workloads specifically, the data partitioning strategy is critical. Poor spatial partitioning leads to skewed workloads in which some workers process far more data than others, degrading parallel efficiency \parencite{tang2020_locationspark_distributed_spatial_query}.

\subsection{Cloud cost model}
The choice between distributed and non-distributed compute is ultimately mediated by a cost model in which every resource---storage, processing, and bandwidth---is separately metered \parencite{mell2011_nist_definition_of_cloud_computing}. Cloud economics exposes this metering as a pay-as-you-go model in which compute and storage are acquired on a short-term basis and released when no longer needed \parencite{armbrust2010_view_of_cloud_computing}. Each resource carries its own pricing dimension: compute is billed for allocated virtual cores in per-minute increments \parencite{microsoft2024_virtual_machines_pricing}; object storage is priced per gigabyte-month across access tiers, with transactional APIs charged per 10,000 operations \parencite{microsoft2024_azure_data_lake_storage_pricing}; and outbound network traffic is billed per gigabyte of egress \parencite{microsoft2024_bandwidth_pricing}. To dampen the volatility of on-demand pricing, providers also offer reserved instances that trade flexibility for lower rates over one- or three-year commitment terms \parencite{microsoft2024_azure_reservations}. Elasticity, therefore, has direct cost implications: serverless platforms charge only for active execution time and scale to zero when idle, whereas long-running clusters continue to accrue charges regardless of utilization \parencite{jonas2019_berkeley_view_on_serverless_computing}.
