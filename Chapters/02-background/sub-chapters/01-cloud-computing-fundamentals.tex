\section{Cloud computing fundamentals}

\subsection{Storage and compute decoupling}
Traditional data processing systems were designed under the assumption that storage and computation live on the same machine (i.e., a node). Data storage and computation are tightly coupled, meaning it processes only the data stored on that node. Both storage and compute must scale together, even when demand grows at different rates due to this tight coupling \parencite{dageville2016_snowflake_elastic_data_warehouse}. 

Cloud architecture decouples the computation and storage into separate layers. The data is stored in object storage, and provisioning compute resources is independent and on-demand. Object storage is inexpensive and more or less limitless in capacity, but it lacks query capabilities. The decoupling allows storage and compute to be scaled, priced, and allocated independently \parencite{wang2024_storage_disaggregated_databases}. The computation can be shut down entirely when not in use \parencite{dageville2016_snowflake_elastic_data_warehouse}. The separation of the compute and storage of data layers allow multiple compute engines to read the same underlying data without coordination through a shared server \parencite{wang2024_storage_disaggregated_databases}. \textcite{dageville2016_snowflake_elastic_data_warehouse} points out that this decoupled architecture incurs higher latency and CPU overhead per request than a node where compute and storage are tightly coupled. This makes format design critical, where formats that minimize data reads per query gain an advantage in this architecture. 

\subsection{Distributed- and non-distributed compute}
\label{sec:distributed-and-non-distributed-compute}
With storage and compute decoupled, the choice of compute model becomes a central architectural decision. Non-distributed compute executes a query entirely within a single process on one machine, with no coordination overhead between workers \parencite{mcsherry2015_scalability_but_at_what_cost}. Distributed compute, by contrast, splits both data and computation across multiple worker nodes coordinated by a driver or scheduler \parencite{stonebraker1986_case_for_shared_nothing}. This distribution introduces overhead. Task scheduling, data shuffling between nodes, serialization, and network communication between workers, all of which add latency before any computation begins \parencite{mcsherry2015_scalability_but_at_what_cost}. As a result, distributed systems only outperform single-node systems when the dataset or computation is large enough to justify the coordination cost \parencite{mcsherry2015_scalability_but_at_what_cost}. For spatial workloads specifically, the data partitioning strategy is critical. Poor spatial partitioning leads to skewed workloads in which some workers process far more data than others, degrading parallel efficiency \parencite{tang2020_locationspark_distributed_spatial_query}.
