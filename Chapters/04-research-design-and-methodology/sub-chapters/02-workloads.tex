\section{Workloads}
\label{research-design-and-methodology:workloads}

The experimental design fixed which factor each research question varies, and which conditions are held constant; this section specifies the workloads that those configurations execute. The workloads are not chosen to cover the query language but to exercise the two structural axes established in the background. The first is the divide between formats a client can read in part and formats that require a full scan, identified in Section~\ref{background:spatial-data-formats-and-storage-models:summary} as the primary axis for interpreting read performance. The second is the distributed query lifecycle of Section~\ref{background:distributed-spatial-processing:the-lifecycle-of-a-distributed-spatial-query}, whose planning, shuffle, and collection phases determine where a distributed engine spends time and bytes. Each workload is therefore mapped to the access or index mechanism it is designed to stress, so that a difference between configurations can be traced to that mechanism rather than to the workload in the aggregate.

\subsection{Workload taxonomy}
\label{research-design-and-methodology:workloads:workload-taxonomy}

The workloads are divided into two families, corresponding to the split between the first two research questions. \acrshort{rq}1 is served by three single-machine query patterns evaluated on one input: a point-in-polygon test, a $k$-nearest-neighbor search, and a bounding-box range filter. \acrshort{rq}2 is served by a single national-scale spatial join between two inputs, evaluated both on the distributed engine and on the single-node engines that serve as its reference. The single-machine patterns isolate how a format and engine read and prune one dataset, whereas the join exercises the cross-input coordination that only a distributed lifecycle incurs.

Each pattern stresses a distinct mechanism. The point-in-polygon test resolves an intersection predicate, the class of predicate for which an R-tree is consulted in both single-node engines (Section~\ref{background:spatial-data-formats-and-storage-models:full-database-engines}), so it measures how effectively that index narrows the candidate set. The $k$-nearest-neighbor search orders features by distance to a fixed point, and distance ordering is not accelerated by the spatial index unless a bounding-box predicate is also supplied (Section~\ref{background:spatial-data-formats-and-storage-models:full-database-engines}), so it probes the cost of a predicate the index does not directly serve. The bounding-box range filter is the pattern that range-request formats are built for: it is answered by block-level pruning against per-row-group statistics and the GeoParquet bounding-box covering (Section~\ref{background:geometry-and-indexing:spatial-indexing}), while the format-level predicate and projection pushdown of Section~\ref{background:spatial-data-formats-and-storage-models:file-formats} govern how many bytes leave storage. The spatial join is a wide operation that crosses a stage boundary and resolves through either broadcast or partitioned execution (Section~\ref{background:distributed-spatial-processing:distributed-spatial-operations}); it is the workload on which the distributed lifecycle of Section~\ref{background:distributed-spatial-processing:the-lifecycle-of-a-distributed-spatial-query} either repays its coordination cost or does not.

\subsection{Workload definitions}
\label{research-design-and-methodology:workloads:workload-definitions}

Each single-machine workload is defined by three elements: the spatial predicate it evaluates, the fixed reference geometry against which the predicate is tested, and the shape of the result it returns. The point-in-polygon workload tests a fixed query point against the building polygons and returns the polygon or polygons that contain it. The $k$-nearest-neighbor workload ranks the buildings by distance to a fixed query point and returns the $k$ closest, for a fixed $k$. The bounding-box workload applies a fixed rectangular window and returns every building whose geometry intersects it, with the window sized to a fixed selectivity so that the fraction of the dataset returned is held constant across tiers. Figure \ref{fig:single-machine-query-definitions} illustrates the three patterns geometrically against a shared building set. Holding the reference geometry and the returned fraction constant across configurations is what allows a difference in time or transferred bytes to be attributed to the format and engine rather than to a difference in how much data each query happened to touch.

The \acrshort{rq}2 workload is a spatial join between Norwegian municipal boundaries and the building dataset, evaluated with an intersection predicate and grouped per municipality, so that each building is associated with the municipality whose boundary contains it. The single-machine patterns are run at a small and a large dataset tier, while the join is run at a small, a medium, and a large tier to trace its scaling behavior; the concrete record counts and the data layer that realizes each tier are described in Chapter~\ref{ch:system-architecture-and-implementation}. \subsection{Iteration counts}
\label{research-design-and-methodology:workloads:iteration-counts}

Every workload is executed as a sequence of warmup iterations followed by timed iterations, with the warmup results discarded, following the replication protocol of Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}. Warmup primes the state that would otherwise contaminate the first timed measurement: the operating-system page cache, the database connection and its query-plan cache, just-in-time-compiled code paths in the engine, and, on the distributed engine, executors that have already been allocated and have read their input once. The number of timed iterations is set per workload on a pragmatic basis rather than from a variance target, with cheap, high-frequency single-machine queries repeated enough times to characterize their distribution, and expensive workloads repeated fewer times. The statistical treatment of the resulting samples, including the estimator and uncertainty quantification, as well as the iteration-count feeds, is given in Section~\ref{research-design-and-methodology:statistical-analysis}.

The national-scale join is the limiting case and is run for seven iterations. Each of its runs provisions and pays for a fresh cluster, so additional iterations multiply provisioning cost without improving the measurement in proportion, and seven is the count at which the per-tier cost of the join was judged acceptable against the information each further run adds. For the same reason, the distributed configuration takes no warmup iterations: a discarded warmup run would provision an entire cluster only to throw the result away, so the warmup discipline applied to the single-node engines is omitted for it, as noted in Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}, and the resulting first-run variance is handled in the analysis rather than removed by priming.
