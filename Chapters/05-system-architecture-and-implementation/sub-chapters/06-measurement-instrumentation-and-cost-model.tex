\subsection{Host-level instrumentation}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:host-level-instrumentation}

Each single-node entrypoint is wrapped by the \texttt{@monitor} decorator, which separates a discarded warmup phase from the timed iterations and records four quantities on every timed iteration: wall-clock elapsed time from \texttt{time.perf\_counter}, process CPU time split into user and system seconds from \texttt{psutil.Process.cpu\_times}, bytes sent and received at the container network interface from \texttt{psutil.net\_io\_counters}, and the cardinality of the result set. Every experiment runs alone in its own \acrshort{aci} container group, named \texttt{benchmark-\{experiment\_id\}}, so the process- and host-level counters read inside that group reflect the configuration under test with no contention from a co-scheduled benchmark. The network volume is the one quantity read at host rather than process scope, which is why a dedicated container group per experiment matters: the bytes it reports over a timed window are accrued by that experiment alone.

The high-frequency single-machine queries, point-in-polygon lookup, k-nearest-neighbor search, and bounding-box filter, follow the sequential stopping rule whose rationale is set out in Section~\ref{research-design-and-methodology:workloads:iteration-counts}. After each timed iteration the decorator recomputes a bootstrap 95\% confidence interval on the mean elapsed time, drawing \num{1000} resamples (\texttt{BENCHMARK\_BOOTSTRAP\_RESAMPLES}), and stops once the interval half-width falls to within 5\% of the mean (\texttt{BENCHMARK\_TARGET\_CI\_HALF\_WIDTH\_RELATIVE}). Two floors must clear before the rule may stop: at least ten successful samples (\texttt{BENCHMARK\_MIN\_ITERATIONS}) and a timed window of at least \SI{60}{\second} (\texttt{BENCHMARK\_MIN\_TIMED\_WINDOW\_SECONDS}). The sixty-second floor exists because the cost model of Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model} reads Azure Monitor counters at one-minute granularity, and a window shorter than a full minute would leave the corresponding metric bucket unpopulated. A soft ceiling at the per-workload iteration budget bounds the loop from above, \num{2500} iterations for point-in-polygon lookup and \num{4000} for k-nearest-neighbor search, but the loop runs past that ceiling when the sixty-second floor has not yet been met. Two hard limits cap a runaway run: a per-iteration timeout of \SI{3600}{\second} (\SI{60}{\minute}, \texttt{BENCHMARK\_MAX\_ITERATION\_SECONDS}) and a cumulative timed-window cap of \SI{6}{\hour} (\texttt{BENCHMARK\_MAX\_TIMED\_WINDOW\_SECONDS}).

The national-scale spatial join takes the fixed branch instead, across the DuckDB, PostGIS, and Databricks configurations, for the reason given in Section~\ref{research-design-and-methodology:workloads:iteration-counts}: each iteration holds a distributed cluster or the shared PostgreSQL instance for its full duration, so a variance-driven rule would multiply cost without a matching gain in precision. These benchmarks set \texttt{use\_sequential\_stopping=False} and run a fixed three timed iterations (\texttt{NATIONAL\_SCALE\_SPATIAL\_JOIN}) after a single warmup (\texttt{warmup\_iterations=1}), since one warmup is enough to prime the engine and additional warmups would dominate the wall-clock budget. A cumulative wall-clock ceiling of \SI{5}{\hour} (\texttt{BENCHMARK\_MAX\_FIXED\_WINDOW\_SECONDS}) bounds this branch, and the \SI{60}{\minute} per-iteration timeout remains in force so that a single stalled iteration cannot run on into unbilled node-hours.

A transient iteration failure does not abort the run. When an iteration raises, the decorator persists it as a per-iteration sample marked \texttt{status="failed"} and proceeds to the next one; only \texttt{BENCHMARK\_MAX\_CONSECUTIVE\_FAILURES}, three failures in a row, abort the loop with \texttt{stop\_reason="failed"}, on the reading that a streak signals a genuinely broken cluster rather than one unlucky scheduling decision. A run that completes normally but recorded at least one failure along the way is tagged \texttt{stop\_reason="partial"}, so the analysis can separate clean runs from mixed ones. The mean, median, and bootstrap confidence interval are computed over the successful samples alone, so a failed iteration raises the failure count without ever entering the elapsed-time distribution.

\subsection{Spark phase metrics}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:spark-phase-metrics}

The host-level counters described in the preceding subsection read only what crosses the boundary of a single container, so they cannot resolve the internal structure of a join that executes across many executors inside a Databricks cluster. The distributed configuration is therefore instrumented from within the run itself. Each Sedona notebook registers a Scala \texttt{SparkListener} whose \texttt{onStageCompleted} callback fires as every stage finishes and accumulates that stage's run-time quantities: the executor run time (\texttt{executorRunTime}), the input bytes read at the executors (\texttt{inputMetrics.bytesRead}), the shuffle bytes read and written (\texttt{shuffleReadMetrics.totalBytesRead} and \texttt{shuffleWriteMetrics.bytesWritten}), and the stage's wall-clock duration. The listener publishes the accumulated totals as the global temporary view \texttt{\_phase\_metrics}. Once the timed join action returns, a final cell sums these columns and emits them, alongside the measured elapsed time and the result cardinality, as a single JSON object through \texttt{dbutils.notebook.exit}. The host process parses that object into a \texttt{DatabricksRunResult}, and the \texttt{@monitor} decorator, run with \texttt{elapsed\_from\_result} enabled, writes the phase metrics onto the same per-iteration sample that carries the host-level counters.

Each recorded quantity stands in for one of the three phases established in Section~\ref{research-design-and-methodology:metrics-and-cost-model:distributed-phase-metrics}. The executor run-time supplies the executor read time, and the shuffle volume is the sum of the shuffle bytes read and written. The driver collection time is not emitted by any single stage and is instead recovered as a residual, the measured wall-clock time less the summed stage durations. This residual absorbs the driver-side work that falls outside the staged execution, chiefly query planning and the final collection of the result. It is clamped to zero on the rare runs where overlapping stages, a side effect of cluster autoscaling, drive the subtraction negative. With executor read time, shuffle volume, and driver collection time each recorded per iteration, the distributed run-time is stored in a decomposed form rather than as a single opaque interval.

\subsection{Cost model implementation}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:cost-model-implementation}

The monetary figure attached to each run is not metered live but computed offline, once the timed window has closed, from two inputs: the observed duration of that window and the resource allocation declared for the configuration. Compute is charged against the allocation the experiment held rather than its measured utilization, so the \acrshort{aci} \acrshort{vcpu} and memory counts and the cluster node count enter the calculation as fixed quantities read from the experiment configuration. This computation instantiates the four-term model of Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}: a compute charge for processing capacity held over the window, a storage charge prorated to the fraction of a 30.44-day month the data occupies, an operations charge per 10{,}000 object-storage requests, and an egress charge per gigabyte of outbound traffic. Each configuration is assembled from only the terms it actually consumes, so a single-node engine reading from object storage accrues compute, storage, operation, and egress terms while a managed-store configuration accrues compute and storage against the relational service instead. Compute is metered at per-second granularity throughout, for the reason given in Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}.

The unit prices are pinned to 2026 Norway East rates and held as constants in the pricing service. Azure Container Instances compute is priced at \$0.0000143 per \acrshort{vcpu}-second and \$0.0000016 per gigabyte-second, applied to the 4 \acrshort{vcpu} and 16 GB held by every single-node container group \parencite{microsoft2024_container_instances_pricing}. Blob storage on the hot tier with \acrfull{lrs} is priced at \$0.022 per gigabyte-month, with object-storage operations at \$0.006 per 10{,}000 reads and \$0.065 per 10{,}000 writes or lists \parencite{microsoft2024_azure_data_lake_storage_pricing}. The relational store, provisioned as a General Purpose \texttt{Standard\_D4ads\_v5} instance, is priced at \$0.476 per compute-hour and \$0.15 per gigabyte-month of storage \parencite{microsoft2024_postgresql_flexible_server_pricing}.

The distributed term combines two charges over the cluster's lifetime in Sweden Central, where the Sedona workers run on \texttt{Standard\_D4s\_v3} nodes under the Jobs Compute plan. Each node draws 0.75 \acrfull{dbu} per hour priced at \$0.15 per \acrshort{dbu}-hour \parencite{databricks2024_pricing}, and each node carries a virtual-machine charge of \$0.204 per hour \parencite{microsoft2024_virtual_machines_pricing}; both are summed across the driver and the workers, since the driver runs on the same node type and is counted alongside them. Egress is the single non-zero transfer charge in the framework. Every transfer that stays within one region and tenant is priced at zero under the modeling assumption of Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}, so only the distributed configuration, whose executors in Sweden Central read storage in Norway East across the regional split established in Section~\ref{system-architecture-and-implementation:infrastructure}, carries an egress charge, billed at the cross-region rate of \$0.02 per gigabyte \parencite{microsoft2024_bandwidth_pricing}. The Jobs Compute Standard tier is retired on 1 October 2026, after which existing workspaces are upgraded to Premium and the \acrshort{dbu} price rises to \$0.30, a revision the pinned constant will require at that date \parencite{databricks2024_pricing}.

\subsection{Raw-sample persistence}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:raw-sample-persistence}

Every timed iteration is persisted in full rather than reduced to a summary at write time. The monitoring storage service writes each iteration's sample as a Parquet object to the benchmarks container, under a Hive-partitioned path keyed by \texttt{query\_id}, \texttt{run\_id}, \texttt{benchmark\_run}, and \texttt{iteration}. The query identifier already carries the dataset size as a suffix (\texttt{-small}, \texttt{-medium}, or \texttt{-large}), so the three size tiers of a single configuration separate into distinct partition prefixes without a dedicated size key. Each row records the wall-clock elapsed time, process CPU user and system seconds, container network bytes sent and received, result cardinality, and a \texttt{status} field marking the iteration as successful or failed, and every row is stamped with schema version \texttt{v4}. Distributed runs add the phase metrics of Section~\ref{research-design-and-methodology:metrics-and-cost-model:distributed-phase-metrics} to the same row: executor read time, shuffle read and write bytes, driver collection time, and the per-stage durations. A Sedona iteration and a single-node iteration therefore share one schema and differ only in which columns are populated.

A separate metadata record summarizes each run. After the iteration loop ends, the service appends one row to \texttt{benchmark\_metadata.parquet} in the metadata container, holding the achieved and failed iteration counts, the \texttt{stop\_reason}, the bootstrapped confidence-interval half-width in both absolute seconds and as a fraction of the mean, and the mean and median elapsed time over the successful samples. The raw samples and this summary together form the persistence contract behind the analysis. Because every iteration is retained as an individual observation, the distribution comparisons, Wilcoxon rank-sum tests, bootstrapped confidence intervals, and Vargha--Delaney $\hat{A}_{12}$ effect sizes of Section~\ref{research-design-and-methodology:statistical-analysis} are recomputed from stored data alone, with no benchmark re-run required. The recorded \texttt{stop\_reason} also carries forward to the execution outcomes examined next.
