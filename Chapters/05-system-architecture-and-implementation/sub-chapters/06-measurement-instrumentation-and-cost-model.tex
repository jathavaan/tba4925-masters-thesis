\subsection{Host-level instrumentation}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:host-level-instrumentation}

The \texttt{@monitor} decorator wraps each single-node entrypoint, separating a discarded warmup phase from the timed iterations and recording four quantities on every timed iteration: wall-clock elapsed time from \texttt{time.perf\_counter}, process CPU time split into user and system seconds from \texttt{psutil.Process.cpu\_times}, bytes sent and received at the container network interface from \texttt{psutil.net\_io\_counters}, and the cardinality of the result set. Every experiment runs alone in its own \acrshort{aci} container group, named \texttt{benchmark-\{experiment\_id\}}, so the process- and host-level counters read inside that group reflect the configuration under test without contention from a co-scheduled benchmark. Network volume is the one quantity read at host rather than process scope, so a dedicated container group per experiment ensures the bytes reported over a timed window are accrued by that experiment alone.

The high-frequency single-machine queries follow the sequential stopping rule whose rationale is set out in Section~\ref{research-design-and-methodology:workloads:iteration-counts}: the point-in-polygon lookup, the k-nearest-neighbor search, and the bounding-box filter. After each timed iteration the decorator recomputes a bootstrap 95\% confidence interval on the mean elapsed time, drawing \num{1000} resamples (\texttt{BENCHMARK\_BOOTSTRAP\_RESAMPLES}), and stops once the interval half-width falls to within 5\% of the mean (\texttt{BENCHMARK\_TARGET\_CI\_HALF\_WIDTH\_RELATIVE}). Two floors must clear before the rule may stop: at least ten successful samples (\texttt{BENCHMARK\_MIN\_ITERATIONS}) and a timed window of at least \SI{60}{\second} (\texttt{BENCHMARK\_MIN\_TIMED\_WINDOW\_SECONDS}). The sixty-second floor exists because the cost model of Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model} reads Azure Monitor counters at one-minute granularity, and a window shorter than a full minute would leave the corresponding metric bucket unpopulated. A soft ceiling bounds the loop from above at the per-workload iteration budget, \num{2500} iterations for point-in-polygon lookup and \num{4000} for k-nearest-neighbor search, but the loop runs past that ceiling while the sixty-second floor remains unmet. Two hard limits cap a runaway run: a per-iteration timeout of \SI{3600}{\second} (\SI{60}{\minute}, \texttt{BENCHMARK\_MAX\_ITERATION\_SECONDS}) and a cumulative timed-window cap of \SI{6}{\hour} (\texttt{BENCHMARK\_MAX\_TIMED\_WINDOW\_SECONDS}). Figure \ref{fig:stopping-rule-control-flow} traces this control flow, from the per-iteration confidence-interval check through the hard caps, the two floors, and the combined half-width-or-budget test that ends the loop.

The national-scale spatial join takes the fixed branch instead, because each iteration holds a distributed cluster or the shared PostgreSQL instance for its full duration, so a variance-driven rule would multiply cost without a matching gain in precision, for the reason given in Section~\ref{research-design-and-methodology:workloads:iteration-counts}. This branch covers the DuckDB, PostGIS, and Databricks configurations. These benchmarks set \texttt{use\_sequential\_stopping=False} and run a fixed three timed iterations (\texttt{NATIONAL\_SCALE\_SPATIAL\_JOIN}) after a single warmup (\texttt{warmup\_iterations=1}), since one warmup is enough to prime the engine and additional warmups would dominate the wall-clock budget. A cumulative wall-clock ceiling of \SI{5}{\hour} (\texttt{BENCHMARK\_MAX\_FIXED\_WINDOW\_SECONDS}) bounds this branch, and the \SI{60}{\minute} per-iteration timeout remains in force so that a single stalled iteration cannot run on into unbilled node-hours.

A transient iteration failure does not abort the run. When an iteration raises, the decorator persists it as a per-iteration sample marked \texttt{status="failed"} and proceeds to the next one. Only three failures in a row (\texttt{BENCHMARK\_MAX\_CONSECUTIVE\_FAILURES}) abort the loop with \texttt{stop\_reason="failed"}, on the reading that a streak signals a genuinely broken cluster rather than one unlucky scheduling decision. A run that completes normally but recorded at least one failure along the way is tagged \texttt{stop\_reason="partial"}, so the analysis can separate clean runs from mixed ones. The mean, median, and bootstrap confidence interval are computed over the successful samples alone, so a failed iteration raises the failure count without entering the elapsed-time distribution.

\subsection{Spark phase metrics}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:spark-phase-metrics}

The host-level counters of the preceding subsection read only what crosses a single container's boundary, so they cannot resolve the internal structure of a join that runs across many executors inside a Databricks cluster. The distributed configuration is therefore instrumented from within the run. Each Sedona notebook registers a Scala \texttt{SparkListener}. Its \texttt{onStageCompleted} callback fires as each stage finishes and accumulates that stage's run-time quantities: the executor run time (\texttt{executorRunTime}), the input bytes read at the executors (\texttt{inputMetrics.bytesRead}), the shuffle bytes read and written (\texttt{shuffleReadMetrics.totalBytesRead} and \texttt{shuffleWriteMetrics.bytesWritten}), and the stage's wall-clock duration. The listener publishes the accumulated totals as the global temporary view \texttt{\_phase\_metrics}. Once the timed join action returns, a final cell sums these columns and emits them, alongside the measured elapsed time and the result cardinality, as a single JSON object through \texttt{dbutils.notebook.exit}. The host process parses that object into a \texttt{DatabricksRunResult}, and the \texttt{@monitor} decorator, run with \texttt{elapsed\_from\_result} enabled, writes the phase metrics onto the same per-iteration sample that carries the host-level counters.

Each recorded quantity stands in for one of the three phases established in Section~\ref{research-design-and-methodology:metrics-and-cost-model:distributed-phase-metrics}. The executor run-time supplies the executor read time, and the shuffle volume is the sum of the shuffle bytes read and written. The driver collection time is recovered as a residual: the measured wall-clock time less the summed stage durations, since no single stage emits it. This residual absorbs the driver-side work that falls outside the staged execution, chiefly query planning and the final collection of the result. It is clamped to zero on the rare runs where overlapping stages, a side effect of cluster autoscaling, drive the subtraction negative. Recording all three terms per iteration leaves the distributed run-time in a decomposed form rather than a single opaque interval.

\subsection{Cost model implementation}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:cost-model-implementation}

Each run's monetary figure is computed offline once the timed window closes, from the window's observed duration and the resource allocation the configuration declared. Compute is charged against the allocation the experiment held rather than its measured utilization, so the \acrshort{aci} \acrshort{vcpu} and memory counts and the cluster node count are read as fixed quantities from the experiment configuration. The computation instantiates the four-term model of Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}. Compute is charged for processing capacity held over the window, storage is prorated to the fraction of a 30.44-day month the data occupies, operations are charged per 10{,}000 object-storage requests, and egress is charged per gigabyte of outbound traffic. Each configuration draws only the terms it consumes: a single-node engine reading from object storage accrues compute, storage, operation, and egress terms, whereas a managed-store configuration accrues compute and storage against the relational service instead. Compute is metered at per-second granularity throughout, for the reason given in Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}.

The unit prices are pinned to 2026 Norway East rates and held as constants in the pricing service; Table~\ref{tab:cost-model-unit-prices} lists them. Container Instances compute is applied to the 4 \acrshort{vcpu} and 16 GB held by every single-node container group, blob storage is billed on the hot tier with \acrfull{lrs}, and the relational store is provisioned as a General Purpose \texttt{Standard\_D4ads\_v5} instance.

The distributed term combines two charges over the cluster's lifetime in Sweden Central, where the Sedona workers run on \texttt{Standard\_D4s\_v3} nodes under the Jobs Compute plan. The first is a \acrshort{dbu} charge, with each node drawing 0.75 \acrlong{dbu}s (\acrshort{dbu}) per hour; the second is a per-node virtual-machine charge. Both are summed across the driver and the workers, since the driver runs on the same node type and is counted alongside them. Egress is the single non-zero transfer charge in the framework. Every transfer that stays within one region and tenant is priced at zero under the modeling assumption of Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}, so only the distributed configuration carries an egress charge, its executors in Sweden Central reading storage in Norway East across the regional split established in Section~\ref{system-architecture-and-implementation:infrastructure}. The Jobs Compute Standard tier is retired on 1 October 2026, after which existing workspaces are upgraded to Premium and the \acrshort{dbu} price rises to \$0.30, which the pinned constant will require updating at that date \parencite{databricks2024_pricing}.

\subsection{Raw-sample persistence}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:raw-sample-persistence}

The framework persists every timed iteration in full rather than reducing it to a summary at write time. The monitoring storage service writes each iteration's sample as a Parquet object to the benchmarks container, under a Hive-partitioned path keyed by \texttt{query\_id}, \texttt{run\_id}, \texttt{benchmark\_run}, and \texttt{iteration}. The query identifier already carries the dataset size as a suffix (\texttt{-small}, \texttt{-medium}, or \texttt{-large}), so the three size tiers of a single configuration separate into distinct partition prefixes without a dedicated size key. Each row records the wall-clock elapsed time, the process CPU user and system seconds, the container network bytes sent and received, the result cardinality, and a \texttt{status} field marking the iteration as successful or failed. Every row is stamped with schema version \texttt{v4}. Distributed runs add the phase metrics of Section~\ref{research-design-and-methodology:metrics-and-cost-model:distributed-phase-metrics} to the same row: executor read time, shuffle read and write bytes, driver collection time, and the per-stage durations. A Sedona iteration and a single-node iteration therefore share one schema and differ only in which columns are populated.

A separate metadata record summarizes each run. After the iteration loop ends, the service appends one row to \texttt{benchmark\_metadata.parquet} in the metadata container, holding the achieved and failed iteration counts, the \texttt{stop\_reason}, the bootstrapped confidence-interval half-width in both absolute seconds and as a fraction of the mean, and the mean and median elapsed time over the successful samples. Retaining every iteration as an individual observation is what lets the analysis recompute the distribution comparisons, Wilcoxon rank-sum tests, bootstrapped confidence intervals, and Vargha--Delaney $\hat{A}_{12}$ effect sizes of Section~\ref{research-design-and-methodology:statistical-analysis} from stored data alone, with no benchmark re-run required. The recorded \texttt{stop\_reason} carries forward to the execution outcomes examined next.

\subsection{Skipping known-infeasible configurations}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:execution-outcomes-and-skipped-cells}

Some cells of the design matrix failed reproducibly: every iteration of the cell ended in the same way, whether through memory exhaustion or by exceeding the per-iteration time ceiling. Once a cell had failed identically across repeated attempts, scheduling it again consumed compute time and Azure spend without yielding a usable measurement. To avoid this, the harness allows a cell to be declared infeasible and excluded from subsequent runs.

The mechanism reuses the \texttt{stop\_reason} field introduced in the preceding subsection. An experiment whose \texttt{benchmarks.yml} entry carries a \texttt{skip} key is detected before any iteration is scheduled: the harness writes a single metadata row recording zero achieved and zero failed iterations together with the declared reason, and returns without persisting any per-iteration sample. A skip is therefore a decision recorded in the configuration rather than an outcome observed at run time, and it is added only after a cell has been seen to fail repeatedly during the benchmark campaign.

Which configurations were declared infeasible, and the consequences of their absence for the comparison, are reported with the rest of the measurements in Chapter~\ref{ch:results} and noted among the design's threats in Table~\ref{tab:threats-validity-summary}. They are not enumerated here, where the concern is only the harness's provision for recording the decision.

\subsection{What is not measured}
\label{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:what-is-not-measured}

The figures reported in this chapter describe a system observed from inside Azure, and several quantities lie outside that frame by construction. The host-level counters read at the container network boundary, as described in Section~\ref{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:host-level-instrumentation}, so the recorded elapsed time is the server-side wall-clock interval from \texttt{time.perf\_counter}, not the end-to-end latency a client would observe. A client outside Azure would add network transit, and possibly application-layer round trips, that the framework never records. Azure-side queueing and scheduling variance is likewise not isolated from the timed figures. It is the shared-infrastructure confound that the design measures of Section~\ref{research-design-and-methodology:threats-to-validity} constrain rather than a quantity the instrumentation resolves into a separate term.

Every timed iteration runs against an engine already brought to steady state by the warmup described in Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}, so the reported numbers characterize a warm engine. Caches are not flushed between successive timed iterations. Any residual benefit from a warm operating-system page cache or from primed connection state is therefore carried inside the steady-state figure rather than separated out as an effect the framework measures in its own right.

Cluster provisioning and termination fall outside the timing window by design, and the cost model computes its figure offline over the timed window alone, as detailed in Section~\ref{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:cost-model-implementation} and Section~\ref{research-design-and-methodology:metrics-and-cost-model:cost-model}, so provisioning and idle time accrue no charge. The reported cost is the cost of running a query on a warm engine, not the cost of cold-starting one for each query. This follows the provision-once discipline of Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization} and the cluster lifecycle of Section~\ref{system-architecture-and-implementation:compute-configuration:apache-sedona-on-databricks}, under which provisioning is a one-time setup cost amortized over many queries in any production deployment. The cost figures that follow therefore isolate query execution from the amortized cost of bringing a cluster into service.
