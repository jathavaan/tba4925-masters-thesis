\section{Architecture overview}
\label{system-architecture-and-implementation:architecture-overview}

The experimental design in Chapter~\ref{ch:methodology} fixes what is varied, what is held constant, and how each outcome is measured; this chapter realizes that design as a running system on Azure. Each experiment runs as an isolated, short-lived containerized job. Every architectural choice answers a single constraint: a difference in elapsed time, transferred bytes, or cost must trace to the configuration under test rather than to the surrounding infrastructure.

Figure~\ref{fig:system-overview} shows the run-time layout. An orchestrator (\texttt{main.py}) runs outside the cluster, reads the experiment manifest \texttt{benchmarks.yml}, and launches one \acrfull{aci} container group per experiment with a restart policy of \texttt{Never}, so each job runs once and is then torn down. Inside each container, a dispatcher (\texttt{benchmark\_runner.py}) matches the experiment's \texttt{script-id} to the entrypoint that implements it. Each entrypoint records its per-iteration samples and a per-benchmark cost row, both written as Parquet to the \texttt{benchmarks} container in Blob Storage for downstream analysis.

The system varies along two axes. On the data axis, one logical dataset of Norwegian building polygons is materialized as three physical representations; on the compute axis, four engines read them, each tied to the access mechanism it exercises. GeoParquet on \acrfull{adls} is read by both DuckDB and Apache Sedona and exercises the range-request access pattern established in Section~\ref{background:spatial-data-formats-and-storage-models:summary}. PostGIS reads the same buildings from server-managed tables, while the Shapefile bundle is read from local disk through GeoPandas as the full-scan baseline. Crossing the cloud-native and traditional axis with the single-node and distributed axis yields the four design cells of Figure~\ref{fig:design-space}.

Section~\ref{system-architecture-and-implementation:infrastructure} fixes the compute platforms, storage, and identity; Section~\ref{system-architecture-and-implementation:data-layer} describes the three data representations; Section~\ref{system-architecture-and-implementation:compute-configuration} sets out each engine's configuration; Section~\ref{system-architecture-and-implementation:orchestration-and-pairing} covers orchestration and pairing; and Section~\ref{system-architecture-and-implementation:measurement-instrumentation-and-cost-model} details the measurement instrumentation and the cost model.
