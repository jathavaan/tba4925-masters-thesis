\section{Infrastructure}
\label{system-architecture-and-implementation:infrastructure}

The benchmarking framework runs within a single Azure resource group\footnote{A resource group is the Azure grouping that holds related resources under a single management and billing boundary.}, \texttt{doppa}, provisioned in Norway East so that every metered resource shares one billing and administrative boundary. The Azure Databricks workspace that hosts the Apache Sedona clusters is the exception, placed in Sweden Central instead. Norway East lacks sufficient \texttt{Standard\_D4s\_v3} quota for the multi-node clusters required by the national-scale spatial join, so the workspace is created where that quota is available. This split is the only source of cross-region traffic in the system: the Sedona executors in Sweden Central read \acrshort{adls} in Norway East, whereas every other configuration keeps its compute and storage within the same region and tenant\footnote{A tenant is the cloud-provider account boundary that isolates one organization's identities and resources from those of others.}. The resulting egress is the single billed transfer in the framework, and its rate enters the cost model in Section~\ref{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:cost-model-implementation}.

\subsection{Compute platforms}
\label{system-architecture-and-implementation:infrastructure:compute-platforms}

Each single-node experiment runs inside its own \acrshort{aci} container group. Every benchmark is a short-lived job that needs an isolated execution unit with no cross-experiment state, and \acrshort{aci} provides this with no orchestrator or node pool persisting between runs. The orchestrator creates one container group per experiment with a restart policy of \texttt{Never}, streams its logs to completion, and deletes the group before the next experiment is dispatched, so each measurement starts from a fresh process on a freshly scheduled host. Query containers are sized at \num{4} \acrfull{vcpu} and \SI{16}{\gibi\byte} of memory, matching the DuckDB and PostGIS client allocations and giving all single-node configurations an identical compute envelope. The outside-cluster orchestrator runs in its own \acrshort{aci} container group sized at \num{2} \acrshort{vcpu} and \SI{2}{\gibi\byte}, since its workload is the serial dispatch loop of Section~\ref{system-architecture-and-implementation:orchestration-and-pairing}, not query execution.

Apache Sedona runs on Azure Databricks classic compute, with one fresh job cluster provisioned per Sedona experiment and terminated in a \texttt{finally} block\footnote{A \texttt{finally} block is the part of a structured exception handler whose code runs whether or not the preceding code raised an error, used here to release the cluster even when an iteration fails.} after the timed iterations complete. Classic clusters expose node type and worker count, both factors of the \acrshort{rq}2 design, whereas serverless compute does not. The driver and every worker run on \texttt{Standard\_D4s\_v3} virtual machines (\num{4} vCore, \SI{16}{\gibi\byte}). Each Sedona node therefore carries the same per-node resource envelope as a single-node \acrshort{aci}, and variation between cluster sizes traces to worker count alone. The runtime is pinned to Databricks Runtime 15.4 \acrfull{lts} (\texttt{15.4.x-scala2.12}). Cluster provisioning, library installation, and the post-run termination all fall outside the timed window, per the warmup discipline established in Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}.

PostGIS runs against an Azure Database for PostgreSQL Flexible Server provisioned in Norway East as a General Purpose \texttt{Standard\_D4ads\_v5} instance (\num{4} vCores, \SI{16}{\gibi\byte} of memory, AMD processor). Storage is Premium \acrfull{ssd} at the P10 performance tier, sized to \SI{128}{\gibi\byte}, with zonal high availability disabled and storage autogrow off. The General Purpose tier was selected over Burstable so that compute capacity is pre-allocated and billed at a flat hourly rate. A Burstable instance would otherwise introduce credit-driven variability in throughput across the long-running national-scale join. The same instance backs every PostGIS workload at every dataset tier, so all PostGIS results share one server configuration and the cost terms developed in Section~\ref{system-architecture-and-implementation:measurement-instrumentation-and-cost-model:cost-model-implementation} apply uniformly.

\subsection{Storage and image registry}
\label{system-architecture-and-implementation:infrastructure:storage-and-image-registry}
A single Azure Blob Storage account backs the framework, holding the GeoParquet building dataset, the Shapefile copy, the municipality boundaries, and every benchmark output written by the entrypoints. Data protection is disabled at the account level, with neither blob nor container soft delete enabled, for an operational reason rather than an experimental one. With soft delete on, the Databricks \acrfull{abfs} driver\footnote{The \acrshort{abfs} driver is the \acrlong{abfs} connector through which Databricks reads and writes Azure Blob Storage.} fails with \acrshort{http}~409 on reads, leaving the Sedona configurations unable to reach the dataset. Disabling soft delete restores those reads, at the cost of the recovery window that would otherwise separate an accidental delete from its permanent removal. That loss is acceptable here because the framework rewrites its outputs from scratch on every run, and the input dataset is reproducible from the setup pipeline.

Container images for every experiment live in a dedicated \acrfull{acr}, \texttt{doppaacr}. The \texttt{push-containers-to-acr.yml} GitHub Actions\footnote{GitHub Actions is a continuous-integration service that runs automated workflows in response to repository events such as a merged pull request.} workflow builds and pushes them on merged pull requests and on manual dispatch. It tags each image as both \texttt{:latest} and a unique identifier, so a benchmark run can be tied back to the exact source revision that produced it. \acrshort{aci} pulls the image from the registry at the start of each experiment, using the tag recorded in \texttt{benchmarks.yml}.

\subsection{Determinism and reproducibility}
\label{system-architecture-and-implementation:infrastructure:determinism-and-reproducibility}

A benchmark run is reproducible because both the set of experiments and the order in which they execute are fixed by data rather than left to chance at launch. The experiment manifest \texttt{benchmarks.yml} enumerates every experiment the suite can run, and the orchestrator reads it once at startup. Before launching any container, \texttt{main.py} shuffles the experiment list with a pseudo-random generator seeded on the run index, \texttt{random.Random(benchmark\_run)}. Execution order is therefore randomized yet identical whenever the same index recurs. This implements the seeded order randomization specified in Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}. Randomizing test-and-control order exposes small slowdowns under cloud variability while keeping the schedule repeatable across re-runs.

Two identifiers key every measurement back to the run that produced it. The run ID is the current date followed by a six-character uppercase-alphanumeric suffix, shared by all experiments in one orchestrated run. The \texttt{benchmark\_run} index counts the repeated passes over the suite, of which the framework performs \texttt{BENCHMARK\_RUNS}, set to \num{30}, and it is the same value that seeds the order shuffle above. The sequential stopping rule introduces a third source of randomness, the bootstrap resampling of elapsed-time samples, and this too is made deterministic. \texttt{\_make\_bootstrap\_rng} derives a seed from a \texttt{blake2b} digest\footnote{A digest is the fixed-size byte string that the \texttt{blake2b} cryptographic hash function computes from its input.} of the \texttt{(run\_id, query\_id)} pair, so a re-run with the same identifiers resamples identically and stops at the same iteration. Figure \ref{fig:determinism-chain} traces each of these sources of randomness back to the fixed identifier that seeds it. This is the concrete implementation of the reproducible stop point established in Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}.

Warmup is configured per workload class rather than uniformly. The \acrshort{rq}1 single-machine queries run \texttt{BENCHMARK\_WARMUP\_ITERATIONS}, set to five warmup iterations whose results are discarded, priming the operating-system page cache\footnote{The operating-system page cache is the region of main memory in which the operating system retains recently read file pages, so later reads are served from memory rather than from disk or network.}, connection state, and any engine hot paths\footnote{A hot path is a frequently executed code path that a language runtime optimizes as it is repeatedly exercised.} before the timed iterations begin. The \acrshort{rq}2 national-scale join overrides this count to a single warmup iteration on every engine that runs it: the single-node DuckDB and PostGIS entrypoints as well as the distributed Sedona variants on Databricks. One warmup suffices to prime the relevant page-cache, connection, and query-plan state on these long, low-variance runs, whereas additional warmups would consume a disproportionate share of the wall-clock budget without improving the timed measurement. This warmup discipline follows the replication protocol of Section~\ref{research-design-and-methodology:overview-and-experimental-design:replication-and-randomization}.
